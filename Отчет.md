# Приложение для электронного тестирования

## Доменная область приложения

Приложение представляет собой систему электронного тестирования знаний. Пользователю необходимо ввести свое имя в соответствии с валидацией, после чего ему будут доступны вопросы теста. После ответа на все вопросы пользователь увидит страницу с результатами: количество баллов, а также верные и неверные ответы.

## Стек реализации

- **Фронтенд:** React, TypeScript, Vite. Раздача статического контента в контейнере осуществляется через веб-сервер Nginx.
- **Бэкенд:** Node.js, Express, TypeScript. Взаимодействие с фронтендом организовано по протоколу HTTP/REST.
- **База данных:** PostgreSQL.

## Основные сущности доменной области

- **Вопрос:** содержит текст вопроса, внешний ключ на правильный вариант ответа и флаг скрытия вопроса.
- **Вариант ответа:** содержит текст варианта ответа и внешний ключ, связывающий его с конкретным вопросом.
- **Результат тестирования:** содержит имя студента, количество набранных баллов, общее число вопросов в тесте и время сдачи.
- **Ответ пользователя:** хранит ответы пользователя на каждый вопрос теста.

## Соответствие методологии 12 факторов

### 1. Кодовая база (codebase)

Весь код проекта (и фронтенд, и бэкенд, и настройки базы данных) хранится в одном общем репозитории. Из него собирается и запускается все приложение.

### 2. Зависимости (dependencies)

Все нужные библиотеки прописаны в файлах `package.json` отдельно для сервера и для клиента. Приложение не зависит от программ, установленных на компьютере. Docker сам скачивает и устанавливает все зависимости внутри изолированных контейнеров.

### 3. Конфигурация (config)

Настройки не зашиты в коде, они хранятся отдельно и считываются через переменные окружения (`process.env` и `import.meta.env`). Секретные файлы `.env` скрыты через `.gitignore`, а для примера созданы файлы `.env.example`. В Docker Compose все настройки передаются через блок `environment`.

### 4. Сторонние сервисы (backing services)

Приложение относится к базе данных PostgreSQL как к подключаемому ресурсу. Сервер общается с ней по сети. Если понадобится переключиться на другую базу данных, менять код не придется — достаточно будет просто указать новый адрес в настройках.

### 5. Сборка, релиз, выполнение (build, release, run)

Процесс запуска разбит на три шага. Сначала идет сборка, где TypeScript компилируется в JavaScript внутри контейнеров. Затем релиз, когда готовый код соединяется с настройками среды. И в конце — выполнение, когда Docker запускает готовые к работе контейнеры.

### 6. Процессы (processes)

Бэкенд-сервер работает без сохранения состояния. Он не хранит файлы или сессии на своем локальном диске — все данные сразу записываются в базу данных PostgreSQL. Благодаря этому можно запустить сколько угодно копий сервера, и они будут работать синхронно.

### 7. Привязка портов (port binding)

Приложению не нужны внешние веб-серверы вроде Apache или Tomcat. Оно само занимает нужные порты в сети: бэкенд работает на порту `5000`, а фронтенд раздается через встроенный Nginx на порту `80` (который для удобства проброшен на порт `5173`).

### 8. Параллелизм (concurrency)

Так как сервер не хранит данные внутри себя, приложение очень легко масштабировать. Если нагрузка вырастет, можно просто запустить несколько одинаковых контейнеров бэкенда за балансировщиком трафика.

### 9. Утилизируемость (disposability)

Контейнеры быстро запускаются и умеют плавно выключаться. Когда приложение останавливают, сервер аккуратно завершает обработку текущих запросов и безопасно закрывает пул соединений с базой данных, ничего не ломая. Также в коде бэкенда настроено автоматическое ожидание базы данных при старте.

### 10. Паритет разработки и продакшена (dev/prod parity)

И на компьютере разработчика, и при запуске в контейнерах используются абсолютно одинаковые версии программ, базы данных и операционной системы. Это гарантирует, что проект запустится одинаково у всех.

### 11. Логирование (logs)

Приложение не создает никаких файлов логов на диске и не занимается их удалением. Все сообщения, действия пользователей и ошибки просто выводятся в консоль сервера. Сбором и отображением этих логов занимается Docker.

### 12. Административные задачи (admin processes)

Все разовые задачи, такие как создание таблиц в базе данных и заполнение их первыми вопросами, полностью автоматизированы. При самом первом запуске PostgreSQL автоматически находит файл `init.sql` и разворачивает всю нужную структуру данных.
