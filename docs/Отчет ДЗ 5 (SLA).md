# Домашнее задание №5. SLA

## 1. Описание выбранных метрик

1. `app_auth_attempts_total` (Counter) — общее количество попыток авторизации администратора. Имеет метку `status` (`success` / `failed`), что позволяет отдельно отслеживать успешные и неудачные входы. Выбрана как SLI доступности админки, потому что доля успешных входов показывает, работает ли панель управления.
2. `app_tests_completed_total` (Counter) — общее количество успешно сданных тестов студентами. Выбрана как SLI пропускной способности, так как показывает, обрабатывает ли система тесты.
3. `app_questions_created_total` (Counter) — общее количество созданных вопросов. Выбрана как SLI пропускной способности админки, поскольку показывает, работает ли CRUD-операция создания.
4. `app_questions_request_duration_seconds` (Histogram) — длительность обработки запросов к `/api/questions`. Имеет метки `method` и `status`. Позволяет вычислять процентили (p50, p95, p99) и выявлять медленные запросы. Выбрана как SLI доступности и скорости API.

## 2. Формулировки SLI, SLO и SLA и формулы их расчета

### 1. Доступность админки (`app_auth_attempts_total{status}`)

#### 1.1. SLI = 82.8%

Из всех попыток входа в админку успешно завершились около 82.8%. Если бэкенд упадет, все попытки будут падать, и SLI упадет до 0.

**Формула:**

```
SLI_1 = sum(rate(app_auth_attempts_total{status="success"}[5m])) / sum(rate(app_auth_attempts_total[5m]))
```

**График SLI:** ![SLI 1](<../screenshots/ДЗ 5 (SLA)/SLI_1.png>)

#### 1.2. SLO = 80%

В течение 30 дней доля успешных входов не должна опускаться ниже 80%. Цель 80% выбрана, чтобы оставался небольшой запас.

**Формула:**

```
SLI_1 ≥ 0.80
```

**Бюджет ошибок:** 20% (допустимо до 20% неудачных попыток входа).

**Формула бюджета ошибок:**

```
1 - SLI_1 ≤ 0.20
```

**График SLO:**

![SLO 1](<../screenshots/ДЗ 5 (SLA)/SLO_1.png>)

#### 1.3. SLA ≥ 75%

Доля успешных входов не должна опуститься ниже 75%.

**Запас:** 80% − 75% = 5 п.п.

**Формула SLA:**

```
SLA(%) = (TWTp - TDtp) / TWTp * 100%
```

Где `TWTp` — общее время работы за период, `TDtp` — суммарное время недоступности.

**График SLA:** ![SLA 1](<../screenshots/ДЗ 5 (SLA)/SLA_1.png>)

### 2. Пропускная способность — тесты (`app_tests_completed_total`)

#### 2.1. SLI = 0.09

Количество успешно сданных тестов в секунду. Показывает, сколько тестов система обрабатывает за единицу времени. Если график падает до 0, значит, что-то сломалось (бэкенд или база).

**Формула:**

```
SLI_2 = sum(rate(app_tests_completed_total[5m]))
```

**График SLI:** ![SLI 2](<../screenshots/ДЗ 5 (SLA)/SLI_2.png>)

#### 2.2. SLO = 0.05

В течение 30 дней система должна стабильно обрабатывать не менее 0.05 успешно сданных тестов в секунду (что эквивалентно 3 тестам в минуту).

**Формула:**

```
SLI_2 ≥ 0.05
```

**Бюджет ошибок:** не рассчитывается в процентах, так как это throughput-SLO (метрика измеряет скорость, а не долю). Критерий нарушения — падение SLI ниже 0.05.

**График SLO:** ![SLO 2](<../screenshots/ДЗ 5 (SLA)/SLO_2.png>)

#### 2.3. SLA ≥ 0.03

Система должна обрабатывать не менее 0.03 успешно сданных тестов в секунду (что эквивалентно 1.8 тестам в минуту).

**Запас:** `(0.05 − 0.03) / 0.05 * 100% = 40%` — SLA на 40% ниже SLO. Запас в процентах, а не в абсолютных единицах, потому что throughput измеряется в «штуках в секунду», и относительное снижение нагляднее.

**Формула SLA:**

```
SLA(%) = (TWTp - TDtp) / TWTp * 100%
```

Где `TWTp` — общее время работы за период, `TDtp` — суммарное время недоступности.

**График SLA:** ![SLA 2](<../screenshots/ДЗ 5 (SLA)/SLA_2.png>)

#### 3.2. SLO = 0.05

В течение 30 дней система должна стабильно создавать не менее 0.05 вопросов в секунду (что эквивалентно 3 вопросам в минуту).

**Формула:**

**График SLO:** ![SLO 3](<../screenshots/ДЗ 5 (SLA)/SLO_3.png>)

#### 3.3. SLA ≥ 0.03

### 4. Доступность API вопросов — доля ошибок (`app_questions_request_duration_seconds_count{status}`)

#### 4.1. SLI = 8.3%

Доля запросов к `/api/questions`, завершившихся ошибкой (`status="500"`). Показывает, какая часть запросов к API вопросов падает с ошибкой сервера. Чем выше значение, тем хуже доступность API.

**Формула:**

```
SLI_4 = sum(rate(app_questions_request_duration_seconds_count{status="500"}[5m])) / sum(rate(app_questions_request_duration_seconds_count[5m]))
```

**График SLI:** ![SLI 4](<../screenshots/ДЗ 5 (SLA)/SLI_4.png>)

#### 4.2. SLO ≤ 15%

В течение 30 дней доля запросов с ошибкой 500 не должна превышать 15%. Цель 15% выбрана с учетом того, что в приложении искусственно генерируется 10% ошибок (middleware `errorSimulator`), поэтому SLI колеблется в диапазоне 2.3% до 13.1%.

**Формула:**

```
SLI_4 ≤ 0.15
```

**Бюджет ошибок:** 15% (допустимо до 15% запросов с ошибкой).

**Формула бюджета ошибок:**

```
SLI_4 ≤ 0.15
```

**График SLO:** ![SLO 4](<../screenshots/ДЗ 5 (SLA)/SLO_4.png>)

#### 4.3. SLA ≤ 20% (доступность ≥ 80%)

Доля запросов с ошибкой не должна превышать 20% (то есть доступность API ≥ 80%).

**Запас:** 20% − 15% = 5 п.п. (SLA мягче SLO на 5 процентных пунктов).

**Формула SLA:**

```
SLA(%) = (TWTp - TDtp) / TWTp * 100%
```

Где `TWTp` — общее время работы за период, `TDtp` — суммарное время недоступности.

**График SLA:** ![SLA 4](<../screenshots/ДЗ 5 (SLA)/SLA_4.png>)

### 5. Скорость ответа API вопросов — p95 (`app_questions_request_duration_seconds_bucket`)

#### 5.1. SLI = 57 мс

95-й процентиль времени ответа на запросы к `/api/questions`. Показывает время, быстрее которого выполняются 95% запросов. Если p95 растет, значит, API начинает работать медленнее (например, из-за роста количества вопросов в базе).

**Формула:**

```
SLI_5 = histogram_quantile(0.95, sum(rate(app_questions_request_duration_seconds_bucket[5m])) by (le))
```

**График SLI:** ![SLI 5](<../screenshots/ДЗ 5 (SLA)/SLI_5.png>)

#### 5.2. SLO = 500 мс

В течение 30 дней 95-й процентиль времени ответа не должен превышать 500 мс. Цель 500 мс выбрана так, чтобы был запас относительно измеренного SLI (57 мс), но при этом SLO оставался чувствительным к деградации.

**Формула:**

```
SLI_5 ≤ 0.5
```

**Бюджет ошибок:** 5% времени за 30 дней (≈36 часов), когда p95 может превышать 500 мс без нарушения SLO.

**Формула бюджета ошибок:**

```
count_over_time((SLI_5 > 0.5)[30d:]) / count_over_time(SLI_5[30d:]) ≤ 0.05
```

Где `SLI_5` — результат запроса `histogram_quantile(0.95, ...)`, а не сырая метрика.

**График SLO:** ![SLO 5](<../screenshots/ДЗ 5 (SLA)/SLO_5.png>)

#### 5.3. SLA ≥ 700 мс

95-й процентиль времени ответа не должен превышать 700 мс.

**Запас:** 700 − 500 = 200 мс.

**Формула SLA:**

```
SLA(%) = (TWTp - TDtp) / TWTp * 100%
```

Где `TWTp` — общее время работы за период, `TDtp` — суммарное время недоступности.

**График SLA:** ![SLA 5](<../screenshots/ДЗ 5 (SLA)/SLA_5.png>)

### 6. Общий SLA ≥ 75%

Общий SLA равен самому слабому детальному SLA (SLA_1 = 75% по доступности админки), потому что общее обещание не может быть сильнее самого слабого звена.

**Формула SLA:**

```
SLA(%) = (TWTp - TDtp) / TWTp * 100%
```

Где `TWTp` — общее время работы за период (30 дней = 720 часов), `TDtp` — суммарное время недоступности.
